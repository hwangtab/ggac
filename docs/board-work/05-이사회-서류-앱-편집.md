# 이사회 서류 앱 편집 — 서류함·자료실의 서류를 앱 안에서 고치고 버전으로 남기기

> 2026-11-05 작성. 사용자 결정: "이사회 서류도 앱편집 넣어". 업무툴 첨부(01
> §7·§8)와 조합원 내 문서함(04)이 이미 가진 앱 편집기(ggac-office 오피스
> iframe·rhwp)·비공개 Blob 직접 업로드·저장본 서버 검사를 **이사회 서류**
> (`board_documents` — 서류함·정기총회·자료실의 '이사회 서류')로 넓힌다.
> 지금까지 서류에는 편집도 버전도 없었다.

## 0. 한 줄 요약

서류를 올린 이사와 관리자는 서류함 목록·서류 화면·자료실에서 **앱에서 편집**을
눌러 DOCX·XLSX·PPTX(오피스 편집기)· HWP·HWPX(rhwp)를 PC에서 고친다. 저장은 늘 새
버전이고 원본은 버전 기록에 남는다. 버전 기록에서 누가 언제 저장했는지 보고,
지나간 버전을 내려받거나 되돌린다(되돌리기 = 그 버전을 복사한 새 버전).
저장·되돌리기 뒤에는 검색 본문을 다시 뽑고, 미리보기 캐시를 지우고, 웹 본문이
있던 서류는 본문을 새 파일로 다시 만든다.

## 1. 결정

1. **누가 고치나** — **지울 수 있는 사람과 같다**: 서류를 올린 사람 또는
   관리자(기존 DELETE 라우트의 `doc.uploaded_by !== user.id && !isAdmin`의
   반대). 그리고 `requireBoardMember()`(이사·감사·관리자)를 지나야 한다. 다른
   이사·감사는 403, 없는 서류는 404. 조합원(조합원 공개 서류를 **읽는** 사람)은
   어떤 편집·버전 라우트도 쓰지 못한다(403). 올린 사람이 없는 시드 서류는
   관리자만 고친다.
2. **형식** — 업무툴과 **같은 env·같은 상한**(`src/work/lib/files/app-edit.ts`):
   - DOCX·XLSX·PPTX(+옛 DOC·XLS·PPT — 저장하면 OOXML) —
     `NEXT_PUBLIC_OFFICE_EDITOR_ORIGIN`, 50MB
   - HWP — 거기에 `NEXT_PUBLIC_HWP_EDITOR_ENABLED=1`, 20MB
   - HWPX — 또 `NEXT_PUBLIC_HWPX_EDITOR_ENABLED=1`
   - PC 전용(업무툴 `useDesktopEditorKnown`). PDF·이미지·텍스트는 편집 진입이
     없다(API 도 415).
3. **원본을 잃지 않는다** — `board_document_versions`(0038). **backfill 없음**:
   처음 저장할 때 같은 트랜잭션에서 지금 `board_documents`의 file*\* 칸을 v1
   행으로 옮기고 v2 를 넣는다. 그 뒤로 `board_documents`의 file*\* 칸은 늘 최신
   버전을 가리킨다 — 목록·다운로드·미리보기·검색·정기총회 화면은 바뀐 것이 없다.
4. **되돌리기는 새 버전** — 고른 버전의 객체를 새 키로 복사하고 새 행을 넣는다.
   지나간 행·객체는 고치지 않는다.
5. **웹 본문(`body_markdown`)** — 본문이 **있던** 서류만 저장 뒤 새 파일에서
   kordoc 마크다운으로 다시 만든다. 없던 서류는 NULL 그대로. 버전 행마다 그
   버전이 최신이던 때의 본문을 남겨 되돌리면 본문도 돌아온다(§5-3).
6. **제목·올린 사람·열람 범위는 바꾸지 않는다** — 편집은 파일만 바꾼다. 그래서
   지우기·편집 권한의 근거(`uploaded_by`)가 그대로다.
7. **이사회 안의 기록** — 버전 기록·지나간 버전 내려받기는 이사·감사·관리자
   누구나(`requireBoardMember`). 조합원은 조합원 공개 서류도 지금 파일만 본다.

## 2. 데이터 모델 (마이그레이션 `0038_board_document_versions.sql`)

업무툴·문서함 관례: 사람 FK는 `member_profiles`, CHECK 없음(허용값은
`editRules.ts`·쿼리 계층), 시각은 epoch ms.

```
board_document_versions         버전 한 벌 = 비공개 Blob 객체 하나
  id            text pk   새 버전은 객체 키의 버전 uuid 구간(= 업로드 id). v1 은 새로 만든 uuid
  document_id   → board_documents.id   ON DELETE CASCADE
  version_no    integer   UNIQUE(document_id, version_no)
  file_path     text      board_documents.file_path 와 같은 규약(접두 `board-documents/` 없이)
  file_name     text      표시 이름(저장본은 지금 이름 본체 + 저장본 확장자)
  file_size     integer
  mime_type     text
  source        'upload' | 'office-editor' | 'hwp-editor' | 'revert'
  created_by    → member_profiles.id   ON DELETE SET NULL (v1 = 올린 사람, 시드 서류는 NULL)
  body_markdown text NULL 그 버전이 최신이던 때의 웹 본문
  created_at    integer(ms)  v1 = 서류를 올린 때
```

- 경로에는 UNIQUE 를 두지 않는다 — v1 은 서류의 옛 경로를 그대로 옮기는데 시드
  서류는 경로를 함께 쓸 수 있다. 같은 업로드를 두 번 승격하는 것은 PK 가 막는다.
- 표 수 86 → **87**(`scripts/testing/migrationAtomicity.test.mjs`),
  `scripts/turso/check-schema-parity.mjs` 목록에 추가.
- 새 버전을 넣는 트랜잭션(`addBoardDocumentVersion`)이 함께 하는 일: 기준 버전
  확인(최신이 아니면 conflict) → (처음이면) v1 행 → 새 행 → `board_documents`
  file\_\*·`body_markdown` 갱신 → `work_board_document_texts` 행 삭제(검색이 옛
  파일의 글자를 내주지 않고, 추출 대상으로 돌아간다).

## 3. 저장소

### 3-1. 경로

```
board-documents/<올린 사람 uuid | seed>/<파일>                  처음 올린 파일(기존) — v1
board-documents/versions/<서류 uuid>/<버전 uuid>/<ASCII 안전 이름>  앱 편집 저장본·되돌리기 복사본
board-work/renders/<서류 id>-…                                  미리보기 캐시(자료실과 공용, 키는 서류 id)
```

- 봉쇄 판정은 `src/lib/storage/boardDocuments.ts`(로컬 import 없음)에 둔다.
  `isSafeBoardDocumentFilePath`가 예전 2구간 모양에 더해 버전
  모양(`versions/<uuid>/<uuid>/<안전 이름>`)도 받는다 — 다운로드·미리보기·추출이
  최신 버전 경로를 그대로 읽어야 하기 때문이다. 형제 판정:
  `isSafeBoardDocumentVersionPath`·`isBoardDocumentVersionPathOf(path, 서류 id)`·
  `isBoardDocumentVersionBlobPathOf`(업로드
  토큰)·`isSafeBoardDocumentBlobPath`(저장소 계층)·
  `boardDocumentVersionFilePath`·`boardDocumentVersionsBlobPrefix`. 시험:
  `boardDocumentVersionPaths.test.mjs`.
- 저장소 계층 `src/lib/boardDocuments/storage.ts`는 업무툴·문서함과 같은 공장
  함수 `createGuardedPrivateStore(isSafeBoardDocumentBlobPath)`로 만든다 —
  `backups/`·`mailbox/`·`board-work/`· `member-documents/`에 닿지 못한다.

### 3-2. 토큰

`privateStoreToken()`(업무툴·문서함과 같다):
`BOARD_WORK_BLOB_READ_WRITE_TOKEN`이 정의돼 있으면(빈 값 포함) 그것만, 아니면
`PRIVATE_BLOB_READ_WRITE_TOKEN`. 기존 서류함 계층(`privateProvider.ts`)은 늘
`PRIVATE_BLOB_READ_WRITE_TOKEN`이므로 **운영에서 두 토큰은 같은 저장소여야
한다** — 지금 운영에는 앞의 변수가 없다(그래서 같은 값). 앞의 변수를 운영에 따로
두려면 이 가정부터 다시 봐야 한다. E2E 는 앞의 변수를 늘 정의해(시험 저장소 토큰
또는 빈 값) 운영 저장소에 닿지 않는다(빈 값이면 503).

### 3-3. 임시 업로드 행을 두지 않는다

문서함은 `member_document_uploads`(임시 업로드 행)를 토큰 발급 근거로 쓴다. 서류
편집은 행 없이 간다: 키가
`versions/<이 서류>/<새 uuid>/<지금 이름에서 만든 안전 이름>`으로 서버가 정한
모양이라, 토큰 발급과 승격이 **같은 판정을 다시** 할 수 있다(이 서류의
키인가·업로드 id 구간이 같은가·형식이 원본과 같은가). 크기는 행 대신 저장소
`head()`의 실제 값으로 본다. 승격 전에 끊긴 저장본(행 없는 객체)은 서류를 지울
때 접두로 찾아 함께 지운다(§6). 표가 하나 줄고 정리 크론이 필요 없다.

## 4. 경로와 게이트

모든 새 API 핸들러의 첫 줄은 `requireBoardMember()`다(비로그인 401·조합원/미승인
403). 그다음 경로 id 모양(UUID 가 아니면 404), 쓰기면 분산 레이트 리밋, 그다음
서류 행과 편집 판정(`editableBoardDocumentOr` — `boardDocumentEditAccess`).

| 경로(`/api/board-room/documents/[id]…`) | 메서드 | 하는 일                                                                                              | 권한                   |
| --------------------------------------- | ------ | ---------------------------------------------------------------------------------------------------- | ---------------------- |
| `/edit-uploads`                         | POST   | ① `prepare`(형식·상한·편집기 env 판정 → 키) ② `@vercel/blob/client` 토큰 요청(이 서류의 버전 키에만) | 올린 사람·관리자       |
| `/versions`                             | GET    | 버전 기록(최신 먼저, 고친 적 없으면 지금 파일 v1 한 줄) + `canEdit`·`editableHere`                   | 이사·감사·관리자       |
| `/versions`                             | POST   | `{ uploadId, name, baseVersionNo }` 저장본 → 새 버전 · `{ revertVersionId }` 되돌리기                | 올린 사람·관리자       |
| `/versions/[versionId]/download`        | GET    | 지나간 버전 내려받기(이 서류의 버전만, 첨부·캐시 금지)                                               | 이사·감사·관리자       |

## 5. 데이터 흐름

### 5-1. 편집기 저장

```
편집 화면(AppEditScreen) ─ 저장 ─▶ 편집기가 내보낸 File(브라우저 검사: 오피스 ZIP 머리·HWP verify)
  ① POST /edit-uploads {type:'prepare', name, size}        → { uploadId, pathname, mime, multipart }
  ② @vercel/blob/client upload(pathname)  ─ 토큰 요청 ─▶ POST /edit-uploads(blob.generate-client-token)
       └ 서버: 이 서류의 버전 키·같은 업로드 id·같은 형식일 때만, 형식 하나·편집기 상한까지·덮어쓰기 없이
  ③ POST /versions {uploadId, name, baseVersionNo}
       └ 서버 saveEditedVersion: head(실제 크기·형식) → 오피스는 PK 머리(범위 읽기) / HWP·HWPX 는
         inspectEditorSave(원본 = 지금 최신 파일, 쪽 수 캐시 키 = 서류 id) → 막히면 객체 지우고 422
         → 웹 본문 정하기(§5-3) → addBoardDocumentVersion(한 트랜잭션, §2) → 실패면 객체 지움(409·404)
         → 검색 본문 다시 뽑기 예약(scheduleBoardDocumentTextExtraction) · 미리보기 캐시 삭제
       └ 라우트: 활동 기록(board_document_version_saved — 서류 id·버전 번호·경로·크기·관리자 여부. 내용·파일 이름 없음)
```

`baseVersionNo`가 지금 최신이 아니면 409(다른 사람이 먼저 저장 — 덮지 않는다).
편집 화면은 저장할 때마다 기준을 방금 만든 버전으로 옮겨 같은 편집기 문서로 계속
고친다(문서함과 같다).

### 5-2. 되돌리기

`revertToVersion`: 이 서류의 버전인지(아니면 404)·최신이 아닌지(최신이면
409)·경로가 안전한지 → 새 uuid 키로 **복사** → 웹 본문(§5-3) →
`addBoardDocumentVersion(source 'revert', revertFromVersionId)`(트랜잭션 안에서
같은 판정을 다시 한다) → 같은 뒤처리 → 활동
기록(`board_document_version_reverted`, `from_version_no`).

### 5-3. 웹 본문(`body_markdown`) — 정한 것과 남은 것

- **저장**: 본문이 있던 서류(`hasWebBody` — 빈 문자열·공백만은 없는 것)만 새
  파일에서 다시 만든다. 다시 만들기는
  `extractMarkdown`(`src/work/lib/files/extract-text.ts` — 검색 추출과 같은
  kordoc·압축 폭탄 검사·OCR 끔·60초 제한)로 kordoc 마크다운에 뷰어와 같은
  정리(`cleanMarkdown`)만 한 것이다. 실패하면(스캔본·형식 실패·200만 자 초과)
  **지금 본문을 그대로 둔다** — 사무국이 다듬은 본문을 잃지 않는다. 화면이 "웹
  본문은 다시 만들지 못해 이전 본문을 두었다"고 알린다.
- **버전 행의 본문 기록** = 그 버전이 최신이던 때의 본문(저장 뒤 서류에 남은
  본문). v1 은 처음 저장 직전의 본문이다.
- **되돌리기**: 고른 버전의 기록이 있으면 그것으로. 기록이 없는데 지금 본문이
  있으면(버전이 생긴 뒤 사무국이 본문을 붙였다) 되돌린 파일에서 다시 만든다. 둘
  다 없으면 NULL(`bodyPlanAfterRevert`).
- **주의(운영 전 확인)**: 정관·총회 자료의 지금 본문은 사무국이
  원문(마크다운)에서 손으로 옮긴 것이다
  (`scripts/import/import-archive-docs.mjs`). 앱에서 한 번 저장하면 그 본문이
  **kordoc 변환본으로 바뀐다** — 표·제목 모양이 달라질 수 있다. 이전 본문은 v1
  기록에 있고 되돌리면 돌아온다. 손으로 다듬은 본문을 유지하려면 앱 편집 뒤
  import 스크립트를 다시 돌린다(그러면 지금 버전 행의 본문 기록과 서류 본문이
  갈라진다 — 기록은 저장 시점의 것이다).
- HWP 원본(OLE)은 kordoc 이 읽지만 본문 품질은 검증하지 않았다 — 지금 운영의
  본문 있는 서류는 마크다운 원문에서 옮긴 PDF·HWP 짝이라 앱 편집 대상(HWP)이 될
  수 있다.

## 6. 삭제·기록

- 서류 삭제(`/api/board-room/documents/[id]` DELETE)는 기존 순서와 근거
  그대로다: **행 먼저**(버전 행은 CASCADE), 그다음 객체 — 실패해도 "저장소에만
  남은 고아 객체"로 끝나 화면이 깨지지 않는다. 버전 경로는 행이 지워지기
  **전에** 읽어 두고 (`listBoardDocumentVersionPaths`), 행을 지운 뒤
  `removeBoardDocumentVersionFiles`가 그 경로들 + 접두
  `board-documents/versions/<서류 id>/` 아래 객체(행 없는 저장본까지)를 지운다.
  봉쇄 판정을 지나지 못한 경로는 건너뛰고 로그만 남긴다. 그 뒤 미리보기
  캐시(기존).
- 활동 기록(`user_activities`):
  `board_document_version_saved`·`board_document_version_reverted`, 대상
  `board_document`. 메타데이터는 버전 번호·경로 종류·크기·되돌린 버전
  번호·관리자 여부뿐 — **문서 내용·파일 이름은 싣지 않는다.** 기록 실패는 저장을
  막지 않고 보안 로그(`BOARD_DOCUMENT_EDIT_AUDIT_FAILED`, high)로 남긴다. 서버
  전용 종류라 브라우저 기록 API 는 받지
  않는다(`SERVER_ONLY_ACTIVITY_ACTION_TYPES`).
- 서버 로그에는 서류 id·상태·오류 이름만 남긴다(본문·파일 내용 없음).
