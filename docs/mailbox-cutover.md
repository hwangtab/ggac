# ggac.kr 메일 수신 전환 체크리스트 — 카카오 스마트워크 → Resend Inbound

이 문서는 비개발자(국장)가 순서대로 따라 할 수 있게 쓴 실행 체크리스트다. 원본
절차는 `docs/superpowers/specs/2026-09-07-admin-mailbox-design.md` 9장이고, 이
문서는 그 6단계를 실행 가능한 체크박스로 옮긴 것이다.

**5단계(루트 MX 교체) 전까지는 카카오 스마트워크가 계속 메일을 받는다 — 유실
없이 언제든 멈출 수 있다.** 5단계를 넘기기 전에 반드시 4단계의 "유입량 기록"
칸을 채우고 판단할 것.

각 단계는 아래 셋을 담는다: **할 일 → 확인 방법 → 되돌리는 법.**

---

## 0단계 — 시작 전에 확인할 것

- [ ] 이 작업은 개발자(코드를 아는 사람)와 함께 진행한다. 3~5단계는 hosting.kr
      DNS 관리 화면과 Resend 대시보드 접근 권한이 필요하다.
- [ ] `TURSO_DATABASE_URL`·`TURSO_AUTH_TOKEN` 등 운영 환경변수에 접근할 수 있는
      사람이 옆에 있다(2단계에서 필요).

---

## 1단계 — 회신 주소부터 고친다 (독립적으로 먼저 배포 가능)

**할 일:** 발신 메일(가입 인증, 비밀번호 재설정 등)에 회신 주소 (`reply_to`)를
붙인다. 지금은 회신 주소가 없어 답장이 `noreply@ggac.kr`로 가서 사라진다.

- [ ] `MAILBOX_REPLY_TO` 환경변수를 Vercel에 등록한다 (예: `office@ggac.kr` —
      실제 받을 주소로 정한다)
- [ ] 회신 주소를 `MAILBOX_ALLOWED_RECIPIENTS`에도 넣었다 — 두 값이 어긋나면 그
      주소로 온 답장의 답장이 에러도 로그도 없이 사라진다 (`npm run env:check`가
      이 조합을 경고로 잡아 준다)
- [ ] 코드 배포 (`git push origin main`)
- [ ] 인증 메일이나 비밀번호 재설정 메일을 실제로 받아서 "회신" 버튼을 눌러 보낸
      곳이 `MAILBOX_REPLY_TO`로 설정한 주소인지 확인한다

**되돌리는 법:** `MAILBOX_REPLY_TO`를 Vercel에서 지운다. 없어도 발송 자체는
그대로 성공한다(전환 전과 동일한 동작).

---

## 2단계 — 메일함 코드 배포 + DB 마이그레이션 적용

⚠️ **배포는 데이터베이스 구조를 바꾸지 않는다.** 코드만 배포하고 마이그레이션을
손으로 적용하지 않으면 화면이 깨진다 — 2026-09-04에 이 실수로 예매 기능이 2.5일
멈춘 전례가 있다. 순서를 반드시 지킨다.

- [ ] **push 전에** 운영 DB의 표 구조를 대조한다(개발자가 `table_info`로 확인)
- [ ] `src/db/migrations/0020_mailbox.sql`을 운영 Turso에 **손으로** 적용한다.
      절차는 `scripts/turso/README.md`의 "적용 방법" 절(0002~0004와 같은
      `executeMultiple()` 경로)을 따른다 — `drizzle-kit migrate`는 쓰지 않는다
- [ ] 적용 후
      `inbound_emails`·`inbound_email_attachments`·`inbound_email_replies` 세
      표가 운영 DB에 생겼는지 확인한다
- [ ] `git push origin main`으로 코드를 배포한다
- [ ] 필수 환경변수 셋을 Vercel에 등록했는지 확인한다: `RESEND_INBOUND_API_KEY`·
      `RESEND_INBOUND_WEBHOOK_SECRET`·`MAILBOX_ALLOWED_RECIPIENTS`
      (`npm run env:check --source=vercel`로 확인 가능)
- [ ] Vercel 프로젝트에 `CRON_SECRET`이 설정돼 있다 — 없으면 새 시간별 백필
      크론(`/api/internal/mailbox/backfill`)이 영원히 401을 받고, 아무도 그
      사실을 모른 채 넘어간다(이 체크 자체가 자동 검사로 잡히지 않는다)
- [ ] 배포 후 `npm run db:parity`를 **운영 URL을 명시해서** 돌린다 — 인자 없이
      돌리면 로컬(`file:local.db`)만 보고 운영을 보지 않는다

**되돌리는 법:** 이 단계에서는 카카오가 여전히 메일을 받고 있으므로 위험이 낮다.
새 표만 추가했으니 마이그레이션을 되돌릴 필요는 보통 없다. 코드를 되돌리려면
이전 배포로 롤백한다(`vercel rollback` 또는 이전 커밋으로 재배포).

---

## 3단계 — Resend에 검증용 도메인을 추가하고 수신을 켠다

**할 일:** 루트 도메인(`ggac.kr`)은 손대지 않고, 검증 전용 서브도메인
`mail.ggac.kr`에만 수신을 연결한다.

- [ ] Resend 대시보드에서 `mail.ggac.kr`을 **Tokyo 리전**으로 도메인 추가한다
- [ ] Resend가 화면에 보여주는 **수신 MX 레코드**를 그대로 hosting.kr DNS에
      추가한다 (`mail.ggac.kr`에만 — `ggac.kr` 루트 MX는 그대로 둔다)
- [ ] 아래 칸에 Resend 화면에 뜬 실제 값을 적어 둔다(문서에 없는 값이라 실물을
      봐야 안다):

  ```
  수신 MX 호스트명: inbound-smtp.ap-northeast-1.amazonaws.com
  우선순위(Priority): 10
  기록 날짜: 2026-09-08

  (Resend 대시보드 mail.ggac.kr 상세 화면에서 확인. 리전 Tokyo.
   같은 화면에서 함께 받은 나머지 레코드 셋:
     TXT   resend._domainkey.mail  → DKIM 공개키
     CNAME rsend.mail              → rsend-apne1.forge.rmta.net
     CNAME send.mail               → send.forge.rmta.net)
  ```

- [ ] Resend 대시보드에서 해당 도메인의 인바운드(Inbound) 설정을 켠다
- [ ] 웹훅 URL을 `https://ggac.kr/api/inbound/resend`로 등록하고, 서명 시크릿을
      `RESEND_INBOUND_WEBHOOK_SECRET`에 등록했는지 다시 확인한다

**되돌리는 법:** hosting.kr에서 `mail.ggac.kr`의 MX 레코드를 지운다. 루트 도메인
MX는 건드리지 않았으므로 `ggac.kr` 메일 수신에는 아무 영향이 없다.

---

## 4단계 — 실제 메일로 검증하고, 유입량을 잰다

**할 일:** `mail.ggac.kr` 주소로 실제 메일을 여러 통 보내 전체 경로가 동작하는지
확인하고, 하루 유입량을 관찰한다.

- [ ] 웹훅이 정상 서명 검증을 통과하는지 확인한다(관리자 메일함
      `/admin/mailbox`에 새 메일이 뜨는지)
- [ ] 본문(html/text)이 제대로 저장되는지 확인한다
- [ ] **첨부파일이 있는 메일을 실제로 보내고, 관리자 화면에서 다운로드해 사람이
      직접 확인한다.** ⚠️ 이 항목은 자동 검사로 걸러지지 않는다 — 다운로드
      배선이 잘못돼 있어도 "파일 없음"과 같은 404 응답을 돌려주기 때문에, 실제로
      파일을 열어서 손상 없이 온전한지, 파일명·확장자가 맞는지 사람 눈으로 봐야
      한다
  - [ ] 다운로드한 파일이 원본과 같은 내용인가?
  - [ ] 파일명이 원래 첨부 이름과 같은가?
  - [ ] 이미지/PDF 등을 열었을 때 깨지지 않고 정상 표시되는가?
- [ ] 답장(reply) 스레딩이 되는지 확인한다(관리자가 답장을 보내면 원 메일에
      묶이는지)
- [ ] `MAILBOX_ALLOWED_RECIPIENTS`에 없는 주소로 보낸 메일이 저장되지 **않는지**
      확인한다(화이트리스트 거름)
- [ ] 첨부 크기 상한을 넘는 메일을 보내 어떻게 처리되는지 확인한다
- [ ] 이 기간(며칠) 동안 하루 평균 수신 건수를 관찰해 아래에 적는다:

  ```
  관찰 기간: __________ ~ __________
  하루 최대 수신 건수: ____ 건
  하루 평균 수신 건수: ____ 건
  ```

- [ ] Resend 대시보드(Settings → Usage)에서 일일·월간 실제 사용량을 확인했다. 위
      "유입량 기록" 칸은 화이트리스트를 통과해 **저장된** 메일만 센 값이다 —
      화이트리스트가 거른 메일도 Resend 쿼터는 이미 먹었으므로, 실제 사용량은 이
      값이 아니라 Resend 대시보드에서만 정확히 보인다
- [ ] **판단:** 위 최대 건수가 Resend Free 한도(하루 100통·월 3,000통, 수신도
      발신과 같은 쿼터를 먹는다)에 견줘 여유가 있는가?
  - **여유가 있다** (예: 하루 최대치가 30건 이하 등, 스팸 유입을 감안해도
    여유롭다) → 5단계로 진행
  - **여유가 없다** → **5단계로 넘어가지 않는다.** 유료 플랜 전환을 검토하거나,
    화이트리스트를 더 좁히거나, 스팸 필터링 방안을 먼저 마련한다

**되돌리는 법:** 3단계와 같다 — `mail.ggac.kr`의 MX 레코드를 지우면 이 검증용
주소로는 더 이상 메일이 오지 않는다. 루트 도메인은 아직 영향받지 않았다.

---

## 5단계 — 루트 MX를 교체한다 (⚠️ 이 단계부터 실제 전환이다)

**전제조건:** 4단계의 "판단"에서 **여유가 있다**로 확인됐을 때만 진행한다.

- [ ] Resend 대시보드(Settings → Usage)에서 일일·월간 실제 사용량을 다시
      확인했다 — 루트 MX를 옮기면 유입량이 늘 수 있으므로 전환 직전에 한 번 더
      본다
- [ ] hosting.kr DNS 관리 화면에서 `ggac.kr` 루트 도메인의 기존 MX 레코드
      `aspmx.daum.net`(우선순위 10)·`alt.aspmx.daum.net`(우선순위 20)을
      **지운다**
- [ ] 3단계에서 기록해 둔 Resend 수신 MX 값을 `ggac.kr` 루트에 추가한다.
      **반드시 그 도메인의 MX 레코드 중 가장 낮은 우선순위 값으로 넣는다** —
      가장 낮지 않으면 메일이 아예 수신되지 않는다(다른 MX가 먼저 응답을
      시도하다 실패해도 재시도로 넘어가지 않을 수 있다)
- [ ] DNS 전파를 기다린다 — **보통 몇 분~수 시간, 최대 24~48시간까지 걸릴 수
      있다.** 전파 중에는 발신 서버마다 오래된 값과 새 값을 섞어 볼 수 있다
- [ ] 전파 확인 후 `ggac.kr`로 실제 메일을 보내 `/admin/mailbox`에서 수신되는지
      확인한다
- [ ] 카카오 스마트워크 쪽으로도 같은 기간 동안 메일이 오는지 병행
      확인한다(들어오지 않으면 전환이 완료된 것)

### 되돌리기 (5단계를 물릴 때)

- [ ] hosting.kr DNS에서 Resend 수신 MX 레코드를 지운다
- [ ] `aspmx.daum.net`(우선순위 10)·`alt.aspmx.daum.net`(우선순위 20)을 다시
      넣는다
- [ ] **DNS 전파 시간이 다시 걸린다** — 되돌린 직후에도 즉시 정상화되지 않을 수
      있으니 몇 시간 여유를 두고 확인한다
- [ ] 되돌리는 동안 두 시스템 어느 쪽에도 오지 않는 메일이 생길 수 있다는 점을
      감안한다(전파 중 발신 서버가 어느 MX를 참조하는지는 예측할 수 없다)

## 6단계 — 정리

- [ ] 루트 SPF 레코드에서 `include:_spf.daum.net`을 뺀다(발신은 `send.ggac.kr`을
      쓰므로 이 항목은 발신에 영향이 없다 — 수신 전환과는 별개로, 더 이상
      카카오를 거치지 않으니 정리하는 것)
- [ ] 검증용으로 추가했던 `mail.ggac.kr` 도메인을 Resend와 hosting.kr 양쪽에서
      정리한다
- [ ] 카카오 스마트워크 쪽 메일 계정을 바로 해지하지 말고, 최소 1~2주는 로그인만
      유지하며 옛 메일이 남아 있는지 확인한다

**되돌리는 법:** SPF에 `include:_spf.daum.net`을 다시 추가한다(전환을 완전히
되돌릴 경우에만 필요 — 5단계를 되돌리는 것만으로 수신은 복구된다).
